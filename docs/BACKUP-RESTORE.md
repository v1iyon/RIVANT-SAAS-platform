# Backup / Restore — как проверить, что это реально работает

Supabase по умолчанию делает ежедневные бэкапы (Point-in-Time Recovery на
платных планах, обычные daily backups на бесплатном). Включённая настройка
сама по себе НЕ значит, что restore реально сработает, когда понадобится —
это нужно проверить руками хотя бы один раз перед релизом и затем повторять
раз в квартал.

## Что проверить один раз перед релизом

1. **Supabase Dashboard → Project Settings → Database → Backups.**
   Убедиться, что бэкапы включены и последний прогон не старше 24ч.
2. **Сделать тестовый restore в отдельный (staging/scratch) проект**, а не
   в production — Supabase позволяет восстановить бэкап в новый проект.
   Dashboard → Backups → выбрать точку восстановления → "Restore to new
   project".
3. **Проверить целостность восстановленных данных** — открыть restored-проект
   и свериться, что:
   - таблицы `subscriptions`, `integrations`, `users`, `metrics_computed`
     на месте и с ожидаемым количеством строк;
   - RLS-политики восстановились вместе со схемой (миграции применяются
     через обычный git-flow, но сами данные — через restore, это два разных
     механизма, стоит убедиться что они не разъехались);
   - `crypto`-зашифрованные поля (`api_key_encrypted` в `integrations`)
     расшифровываются тем же `ENCRYPTION_KEY` — если ключ хранится ТОЛЬКО в
     Vercel/GitHub Secrets и не задокументирован отдельно, восстановленная
     БД будет бесполезна без него. Держать актуальную копию `ENCRYPTION_KEY`
     где-то отдельно от Supabase (например, в менеджере паролей).
4. **Удалить тестовый restored-проект** после проверки, чтобы не платить за
   лишний инстанс.

## На что обратить внимание отдельно

- PITR (Point-in-Time Recovery) на бесплатном плане Supabase недоступен —
  только daily backups с ограниченной глубиной хранения (обычно 7 дней).
  Если план бесплатный, стоит явно понимать: восстановиться можно только на
  начало одного из последних 7 дней, а не на конкретную минуту перед
  инцидентом.
- Этот процесс не автоматизирован и не может быть — это ручная проверка
  инфраструктуры, не код. Стоит завести напоминание (календарь/таск-трекер)
  повторять её раз в квартал, а не полагаться, что "раз проверили — значит
  работает всегда".
